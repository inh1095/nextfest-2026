# Next Fest 전체 목록 확장 설계

상태: 공식 목록·메타데이터·데모 매핑 및 첫 전체 CCU 관측 검증 완료. 원격 운영 전환은 진행 중이다. 첫 관측 확보가 전체 게임의 성장·원인 분석 완료를 뜻하지 않는다.

## 목적과 모집단

공식 행사에 포함된 게임을 빠짐없이 목록에 남기고, 확보한 관측에서 언제 얼마나 변했으며 주변에 어떤 공개 사건이 있었는지 확인한다. 매핑이나 관측이 실패한 게임도 목록에서 제거하지 않는다.

모집단은 공식 행사 페이지 구성 데이터의 특정 시점 스냅샷으로 정의한다. 행사 식별자, 원천 주소, 수집 시각, 국가·언어·로그인·필터 조건, 원천 항목 수, 중복 제거 후 게임 수, 누락·실패를 기록한다. 공식 구성 목록과 이용자별 검색·추천 노출은 구분한다.

SOL 검증 결과, 공식 행사 구성의 `tagged_items`와 section 70212 캡슐은 각각 7,164개이며 ID 집합 차집합은 0이다. 모든 항목은 game이고 고유 AppID는 7,164개다. 미국·한국 구성 목록도 동일하다. 공식 메타데이터 72개 배치의 요청·응답 ID 집합은 일치하며 중복·누락 없이 모두 HTTP 200이었다. 단일 고유 데모 연결은 7,163개, 연결 미확보는 1개이며 서로 다른 다중 데모는 없었다. 원시 응답에 반복된 동일 데모 ID는 중복 제거했다. 지역별 검색 노출 수(US 7,162, KR 6,939)는 등록 모집단을 대체하지 않는다. 부트스트랩 데모 300개도 부분 목록이다. 원천 검증 근거는 `docs/catalog-evidence.json`에 보존한다.

## 진척을 구분하는 상태

| 상태 | 의미 | 완료로 해석하면 안 되는 것 |
| --- | --- | --- |
| 목록 확보 | 공식 스냅샷의 항목을 기록함 | 현재 모든 지역의 모든 노출을 입증함 |
| 메타데이터 확인 | 제목·본편 식별자 등을 공식 자료로 확인함 | 데모 연결 또는 관측 성공 |
| 데모 연결 확인 | 본편과 관측할 데모의 관계를 확인함 | 플레이어 수 확보 |
| 첫 정상 관측 | 실제 API 정상 응답 1개 이상 | 성장 추세나 원인 분석 |
| 비교 가능한 관측 | 실패·긴 공백을 제외한 유효 인접 관측 2개 이상 | 통계적 급증 또는 흥행 성공 |
| 증가 후보 | 정의한 비교 규칙에서 양의 변화가 확인됨 | 원인 확정 |
| 근거 검토 | 적용 구간과 근거를 특정해 검토함 | 이후의 모든 표본까지 검토함 |

각 집계는 전체 목록 수 또는 연결된 데모 수 등 분모를 명시한다. `mapping_missing`, `mapping_ambiguous`, `metadata_error`, `collection_error`, `not_yet_attempted`는 별도 상태다. 여러 데모를 가진 게임은 확인 없이 첫 ID를 선택하거나 인원을 합산하지 않는다.

## 확정된 수집 정책

한 행사 동안의 정적 JSON·CSV와 GitHub Actions 구조를 유지한다. 서버 DB 도입을 전제로 하지 않는다.

- 기존 두 게임은 확보한 이력을 유지하며 전체 요청 예산 안에서 20분 목표 주기로 우선 관측한다. 예산 소진 시 이 두 게임도 중단될 수 있으므로 무조건 보장하는 주기로 표시하지 않는다.
- 전체 데모는 안정적인 식별자 순서와 영속 cursor로 순환한다. 정기 실행당 CCU 700회(기존 두 게임 포함), 공식 공지 360회, 실행 간격 20분, 전역 요청 시작 간격 0.5초 이상, I/O 동시성 최대 4다. 모든 재시도를 같은 limiter와 예산 경로에 포함한다.
- 카탈로그 7,164개 중 실제 CCU 대상은 데모가 연결된 7,163개다. 700회 중 2회를 기존 우선 대상에 쓰고 나머지 7,161개를 698회씩 처리하면 명목 전체 회전은 11회 실행, 약 220분이다. 뉴스 대상은 본편 7,164개와 데모 7,163개를 합한 14,327개 출처다. 이를 실행당 360회씩 처리하는 명목 전체 회전은 약 800분이다. 재시도도 예산을 쓰므로 실제 간격은 더 길 수 있으며 성공 관측 수와 요청 수를 구분한다.
- 요청 횟수 상한과 별도로 수집 실행 마감 약 14분, workflow 약 18분을 두어 검증·저장·게시 시간을 남긴다. 최대 1,060요청 × 하루 72회는 76,320회이며, 초기 수집·추가 메타데이터·탐색 호출도 예산에 포함한다. 재시도는 실행당 요청 상한 안에서 소비한다. 이 프로젝트의 일일 요청 예산은 UTC 날짜 기준 90,000회로 제한하며 공급자 전체 사용량을 보장하는 수치로 표현하지 않는다.
- 공식 공지는 별도 cursor와 호출 예산으로 전체를 순환한다. 최초 전체 조회와 각 게임의 마지막 성공 시각을 기록한다. 본편·데모의 공지를 모두 조회한다면 실제 요청 수는 게임 수보다 많다.
- CCU의 시도·정상 관측 시각, 공지의 시도·전체 출처 확인 시각, 메타데이터 확인 시각과 대상별 목표 주기를 구분한다. 모든 게임을 20분마다 관측한다고 표시하지 않는다.

정책과 코드 구현은 확정됐지만 전체 실제 회전 시간은 운영 실행으로 추가 확인해야 한다. 전체 회전이 수 시간이므로 짧은 방송 직후 피크를 놓칠 수 있다. 증가 시점은 두 관측 사이 구간으로만 표현하고 정확한 발생 분을 추정하지 않는다.

### 현재 자동화에 포함되지 않은 범위

- 증가 후보에 대한 별도 예산의 추가 공지 확인은 미구현이다. 현재는 전체 공지 순환만 수행한다.
- 하루 단위 공식 목록 재탐색과 신규 항목 자동 추가는 미구현이다. 현재 모집단은 검증된 공식 행사 스냅샷이다.
- 영상·방송 전수 자동 검색, 상시 LLM 원인 분석, 모든 게임의 수동 근거 검토는 제공하지 않는다. 초기 검증 사건과 실제 수집한 공식 공지만 근거로 사용한다.

## 오류·종료·보존

- 실패는 값 `null`과 오류 코드로 기록하고 이전 정상값을 보존한다. 최초 시도 전 상태와 정상 응답 0을 구분한다.
- 일부 실패가 전체 결과 저장을 취소하지 않게 한다. 실패한 항목도 기본 cursor는 전진시키고 재시도 대상은 별도로 관리한다.
- 429·일시 오류에는 backoff를 적용한다. 한 게임의 재시도가 작업 전체를 점유하지 않게 한다.
- 저장과 cursor 진행은 함께 확정한다. 처리하지 않은 항목을 처리 완료로 넘기거나, 재실행 때 같은 시각의 관측을 중복 기록하지 않는다. 요청 사용량을 runner 종료 시에만 저장하면 취소·timeout으로 소비량이 사라질 수 있다. 실행 전 요청 예산 예약분을 원격 ledger에 보존한다. 현재 구현은 완료해도 미사용 예약분을 반환하지 않는 보수적 정책이다. 일일 예산은 실제 호출 수가 아닌 예약 allowance의 합계로 차감하며 실제 used는 별도 기록한다. 따라서 예산 제한이 실제 호출 90,000회보다 먼저 발생할 수 있다. 시작된 미완료 예약 및 다른 UTC 날짜의 예약은 다시 사용하지 않고 새 실행 ID로 예약한다. GitHub 실행 ID에는 run_attempt를 포함한다. 초기 SOL 수집 호출과 탐색 예약도 같은 예산에 반영하며 정확하지 않은 탐색 호출 수를 실제 계측값으로 표시하지 않는다.
- 실제 요청·재시도 직전 행사 종료 시각을 검사한다. 종료 후에는 미처리 대상도 미처리 상태 그대로 보관하며 관측을 만들어 채우지 않는다.
- 종료 전에 저장된 원본·요약을 게시한 뒤 자동화를 비활성화한다. 아카이브에 최종 coverage와 실패·미처리 수를 남긴다.
- 최초 두 게임의 원본 관측과 분석의 적용 구간·검토 시각을 보존한다. 전체 확장 이전의 값은 새 게임에 백필하지 않는다.

## 정적 데이터와 화면 성능

| 파일 역할 | 포함할 내용 | 읽는 시점 |
| --- | --- | --- |
| 카탈로그 | ID·이름·간단한 분류·매핑 상태·원천 확인 시각 | 전체 검색·필터 |
| 요약 | 최신값·신선도·표본 수·첫/마지막 관측·기간별 통계·검토 상태 | 개요·전체 목록·정렬 |
| 게임별 상세 | 실제 표본·오류·공개 사건·고정 검토 분석 | 해당 게임 선택 시 |
| 전체 coverage | 단계별 분자·분모·순환 진척·실패·수집 범위 | 개요·수집 상태 |

초기 목록을 표시하기 위해 모든 게임의 시계열·공지 본문을 내려받지 않는다. 요약의 기간별 통계는 수집 후 코드에서 계산해 동일한 기간 기준을 사용한다. 전체 검색·정렬은 작은 목록과 요약에서 수행하고 화면 행은 페이지 단위로 렌더링한다. 자세한 공지 본문·이미지는 필요한 게임에만 로드한다.

동일 snapshot/version의 파일을 함께 게시한다. 상세와 요약의 버전이 어긋나거나 상세 조회가 실패하면 기존 선택의 자료를 보존하고 상태를 표시한다. 로딩 중 다른 게임을 선택했을 때 늦게 도착한 이전 응답이 현재 상세를 덮어쓰지 않아야 한다.

현재 화면은 `catalog.json`, `summary.json`, `events-index.json`으로 전체 탐색을 시작하고 게임별 `history_url`을 선택 시 조회한다. 목록은 25·50행 단위, 동시 비교는 최대 4개, 상세 캐시는 최대 12개다. 분석 게임 선택기는 검색 결과를 20개씩 제공한다.

## 분석 유효성과 편향

기존 70분 공백 기준을 전체 게임에 그대로 적용하면 수 시간 주기의 정상 관측도 전부 끊긴다. 대상별 목표 수집 간격을 기록하고 신선도·비교 가능 간격을 그 주기에 맞춰 정의한다. 실제 관측 간격을 증가 행에 표시한다.

절대 증가량, 증가율, 현재 동접과 관측 최고는 별도 지표로 정렬한다. 증가율의 기준값이 0이면 계산하지 않는다. 관측 한 번인 게임을 순위의 0점 또는 실패로 취급하지 않는다. 관측 주기가 다른 게임의 증가량을 동일한 시간의 성장 속도로 설명하지 않는다.

전체 순위에는 동일 조회 기간과 최소 관측 조건, 실제 관측 범위·간격·신선도를 함께 제공한다. 상대 변화율만 높은 작은 분모, 누락이 많은 게임, 먼저 수집된 게임이 과대 노출되지 않도록 조건과 제외 사유를 공개한다. 단순 양의 변화를 통계적 이상치라고 명명하지 않는다.

주변 사건 검색 범위는 명시하고 선행·구간 내·후행을 구분한다. 성긴 관측에서는 구간 내 사건이 증가보다 먼저 발생했는지 알 수 없다. 공개 뉴스 수집이 아직 순환하지 않은 게임의 사건 0건은 홍보·활동이 없다는 뜻이 아니다.

## 완료 기준

- 공식 목록 스냅샷의 ID 집합과 카탈로그를 대조하고 빠진 ID가 없거나 예외 사유가 명확하다.
- 모든 게임이 매핑·대기·관측·실패 등의 실제 상태로 검색된다.
- 전체 순환이 특정 순위·장르·인기도에 편중되지 않고 종료 시점까지 진척을 측정할 수 있다.
- 예산·제한·부분 실패·재실행·종료 직전에서도 기존 자료와 cursor가 일관된다.
- 단일 관측·0분모·긴 공백·기간 밖 고점·서로 다른 주기·서로 다른 수집 시작을 올바르게 처리한다.
- 전체 카탈로그에서도 검색·정렬·페이지 이동과 상세 지연 로딩이 사용 가능하고 요청·메모리·렌더 비용이 전체 시계열 크기에 비례하지 않는다.
- 완료 보고는 목록 포함·데모 매핑·관측·비교 가능·검토 건수를 구분한다. 전체 목록을 등록한 사실을 모든 게임의 원인 분석 완료로 바꾸지 않는다.


## 수집기 독립 회귀 검증

`tests/test_fleet_review.py`의 독립 검토 회귀 10개와 full/정기 cursor 분리 회귀 1개가 통과했다. 모든 쓰기는 TemporaryDirectory 안에서만 수행했고 실제 네트워크 요청은 하지 않았다.

- 시작된 미완료 예약 및 다른 UTC 날짜의 예약으로 실제 수집을 재개하지 않음.
- 완료한 예약의 미사용분도 일일 한도에서 보수적으로 차감함.
- 동일 슬롯의 기존 관측을 건너뛴 항목도 연속 처리 prefix에 포함해 cursor가 진행함.
- 앞 항목이 예산·시간 제한으로 미처리됐을 때 뒤 항목의 성공만으로 앞 항목을 건너뛰지 않음.
- 우선 대상의 호출을 일반 순환 cursor 진행에 더하지 않음.
- 최근 수집 오류가 있어도 과거 비교 가능한 유효 관측 쌍을 coverage에서 보존함.
- 한 뉴스 출처만 갱신해도 전체 출처 확인 시각은 각 출처 마지막 성공 시각 중 오래된 값으로 유지함.
- 일부 뉴스 출처만 조회했을 때 전체 확인 성공으로 표시하지 않음.
- archive 시각은 설정 종료 시각이 아니라 실제 최초 종료 처리 시각이며 이후 재실행에도 보존함.

실제 운영 전환에서는 최초 두 게임의 기존 원격 수집이 전환 중 추가한 표본까지 shard에 추가 병합하고 원본의 표본·이벤트·분석이 부분집합으로 보존됐는지 확인해야 한다. `merge_legacy.py`는 동일 식별자의 내용 충돌 시 쓰기 전에 중단하며 중복 없이 병합한다. 초기 full 모드는 `full_ccu_cursor`, 정기 순환은 `ccu_cursor`로 좌표를 분리했다. 분리 이전 코드로 시작한 초기 실수집 결과를 전환할 때에는 정기 cursor를 별도 확인해야 한다.

원격 예산 사전 예약, 전체 초기 관측의 완료·오류 수, 전체 뉴스 첫 순환, 실제 Actions 및 Pages 전환은 위 단위테스트 통과와 별개로 확인한다.

## 전체 목록 화면 독립 검토

로컬 구현을 대상으로 다음을 실제 브라우저에서 확인했다. 운영 데이터에는 쓰지 않았으며 오류·경합 사례는 메모리 응답 fixture로 검증했다.

- 실제 7,164개 목록의 첫 화면에서 게임별 이력 요청은 0건이었다. 25행·50행 표시와 다음 페이지 이동, AppID 검색, 데모 미확보 1개 게임의 검색·상태 표시가 동작했다.
- 최대 4개를 선택한 뒤 다섯 번째 선택이 비활성화됐고 선택한 4개에 대해서만 상세를 요청했다.
- 정상 0 → 10 뒤 수집 오류가 있는 fixture에서 증가 구간과 주변 사건을 표시하고, 마지막 오류도 원자료 표와 CSV에 보존했다.
- 단일 관측은 점 1개만 표시하며 증가 구간이나 추세선을 만들지 않았다. 데모 미확보·빈 이력을 0명으로 표시하지 않았다.
- 늦게 도착한 이전 게임 응답이 새 선택을 덮어쓰지 않았다. 상세 503 응답의 오류·재시도 표시와 이후 복구가 동작했다.
- 전체 출처 확인 시각과 마지막 뉴스 시도 시각을 구분하는 소스 수정, 과거 유효 관측 쌍 보유와 최근 인접 비교 가능의 문구 분리를 확인했다.
- 기간 최대 증가 정렬, 최대 증가의 실제 구간 링크, 개요 진입 버튼을 소스에서 확인했다. 최근 증가량만으로 기간의 이전 급증을 놓치지 않게 한다.

위 결과는 로컬 소스·화면 검토다. 전체 뉴스 최초 순환, 원격 운영 전환, 실제 정기 실행 성공 및 게시 결과는 아직 완료로 판정하지 않았다.

## 최초 전체 관측 결과

SOL은 2026-10-20 09:12:45~09:45:28 UTC에 신규 게임 7,161개를 관측했다. 전부 정상이며 양수 2,665개·정상 0명 4,496개였다. 기존 두 게임을 포함해 정상 관측 게임은 7,163개, 데모 미확보 1개, 미처리·최종 오류 0개다. 관측 시각은 게임별로 다르며 동시 스냅샷이 아니다.

실제 요청 7,163회에는 추가 재시도 2회가 포함됐다. 일시 재시도의 원인은 당시 로그가 보존하지 않아 확인하지 못했다. 뉴스 요청은 없었고 별도 순환 수집 대상이다. 상세 대조 결과는 `docs/initial-fleet-ccu.json`에 저장했다.

원격 기준이 추가로 바뀌지 않았음을 확인한 뒤 `merge_legacy.py`를 실행했다. 추가 병합 0건이며 기존 두 게임의 관측·이벤트·분석 전체가 shard에 보존됐다. 초기 코드의 cursor 7,161은 정기 대상 7,161개에 대한 같은 위치인 0으로 정규화했고, `full_ccu_cursor`도 완료 위치 0으로 설정했다.

## 자동 실행 보완

GitHub workflow 예약은 활성 상태이지만 초기 검증 시점까지 native `schedule` 실행 이력은 없었다. 성공한 push/수동 실행을 예약 실행 성공으로 해석하지 않는다. PC가 켜져 있을 때 GitHub 수집 지연을 감시하는 보조 timer를 별도로 준비한다. 이는 PC가 꺼진 상태의 예약 동작을 입증하지 않는다.

workflow 자체는 실행 전 최근 실제 수집 시작으로부터 15분이 지났는지 확인한다. 너무 가까운 중복 발화는 요청 예산을 예약하지 않고 저장된 인덱스만 게시한다. 행사 종료 후에는 이 간격과 관계없이 외부 API 없는 최종 archive 처리를 허용한다.
